# Frontend feature

Build each page in the order of the steps. Each step ends on a check. The rules are in `docs/frontend/`, and this skill links to them.

Before you start, read [frontend.md](../../../docs/frontend.md), [server-state.md](../../../docs/frontend/server-state.md), [client-state.md](../../../docs/frontend/client-state.md), [code-style.md](../../../docs/frontend/code-style.md), [testing.md](../../../docs/frontend/testing.md), and the rules and "In the SPA" of [messages.md](../../../docs/messages.md).

## Steps

Put the code of an area in `frontend/src/domain/<area>/`: the hooks and the keys in `apis/`, and the components in `components/`. Put the pages in the route folder of their URL, such as `frontend/src/routes/members/` for the `users` area. If the area already has keys, components, a builder, or an API file, add to them, and run their tests after each change.

1. **The contract.** The Server endpoints exist, and the generated client is current. Use the `backend-feature` skill for the Server and the `api-contract` skill for the client. The list endpoint takes a page number, a page size, and a search or a filter. The DTO has `allowedActions` and `version`. Each text field and number field of a request DTO has a limit in the contract, and so does the `search` query parameter (`[MaxLength]` on the handler parameter, frontend.md). Done when `src/api/generated/<tag>/clients/` has a client for each call, and `maxLengthOf` and `maximumOf` do not throw for the fields of the form.
2. **The keys and the hooks.** Write `<area>.keys.ts` (server-state.md, "Key factory"). Give all the params of the list to the list key. When the area has a list and a picker, give each its own key under `lists()`, because one is a `useQuery` and one a `useInfiniteQuery` and they cannot share a cache entry. Write one hook for each call: the list with `keepPreviousData` and `parsePagination`, the detail as `queryOptions`, the picker search with `useInfiniteQuery`, and one mutation for each write. Make each mutation update the cache as the table below says. Done when `pnpm lint` passes: it fails on a value that the query function reads and the key does not have.
3. **The list page.** Read `search` and `page` from the URL with `validateSearch`. Build the schema from the generated query schemas with `.catch(undefined)`, so that a bad URL falls back to the default (client-state.md). If the list takes QueryKit `filters` and no `search`, write the `search` schema by hand, and turn the text into a filter in a pure function with a unit test. QueryKit has no escape in a quoted value: put text with a `"` in a raw string (`"""text"""`), and test it on the Server. Show each state with an early return: loading (`role="status"`), error (`QueryError`), empty on a page after page 1 (a link to page 1), empty for a search (the search in quotes), and empty (how to add one, if the area has a create page). Copy the search box of the reference list into the area, and take its `maxLength` from the contract. A `filters` parameter has no limit in the contract, so use the longest field that the filter matches. Send the search after the debounce with `replace: true`, and only when the URL still has the search that the box started from. Give the table `aria-label`, and give `whitespace-nowrap` to each cell that is not prose (code-style.md, "Styles"). A list of tenant data waits for `useMembership`, and shows a link to `/start-tenant` when the user has no tenant. Done when the page in the URL survives a reload, and Back from a detail page shows the list with its search in the box. The search uses `replace: true`, so Back does not step through the typed searches.
4. **The detail page.** Return early for loading and error. Show the title in `PageHeading`. Show a button only for each entry of `allowedActions` (server-state.md, rule 8). An action that needs input, such as a role, asks for it in a form in the dialog. Give each option of that form its label in a `Record` too (messages.md). Give each action its label in a `Record` of the generated union, so that a new action on the Server fails the build until it has a label. Ask for a confirm in a `ResponsiveDialog` before an action that cannot be undone. Read the JSDoc of `components/ui/responsive-dialog.tsx` for the gap under the header. After an action, move the focus to the heading. Done when a user with no permission sees no button.
5. **The edit form.** The page renders the form only after the detail query has data, and only when `allowedActions` has `Update`. Otherwise it says why. The form schema takes each limit from the generated Zod schema of the request DTO (frontend.md, "Forms"). Put the `version` in `defaultValues` and in the PUT body (server-state.md, "Forms with server data"). Use `shouldFocusError: false` with `focusFirstError`. Before a save, clear the refusals. After a refusal, show it with `useServerErrors`. For a stale save (a 409 with the stale-version type), copy `stale-version-alert.tsx` into the area, keep the edits in the form and show an alert in the words of messages.md: what happened, that the edits are not saved, and what to do next. Its button refetches the detail query and resets the form with the new record. Each field that the new record did not change keeps the edit of the user (`latestOverEdits`). A note names the fields that changed, and the focus goes to the first of them. Do not send the PUT again with the new version. After a save, show a toast with `Notification.success` and go to the detail page. Done when the component test of the stale save passes.
6. **The create form.** Do step 5 with no `version`. A create that gets a 409 keeps the input of the user. After a save, go to the detail page of the new record.
7. **The search picker.** Build it on `Combobox` with the `items` prop, so that React Aria does not filter again what the Server filtered. Load the picked record by its ID with the detail hook. Put the pick first in the options when no loaded page has it. The text of the input after a pick is the name of the pick, so it is not a search. On a pick, put the record in the detail cache. Load the next page with `ComboboxLoadMore`. In a form, wrap the picker in a `Controller`, and give `field.ref` to the input. Done when a pick from page 2 and a pick from a link show their names, and a rename shows after the detail query reads the record again.
8. **The tests.** Use the `writing-tests` skill. Write a unit test for each schema with a limit. Write component tests for the stale save of the edit form, the off-page pick of the picker, and the search and the page of the list in the URL. Write a builder in `tests/support/builders/` and an API file in `tests/support/api/` for the area, or add to the ones that exist, then a functional spec that goes from the list to the detail and the edit form. Read back the list query and the PUT body with `api.last`. Done when `pnpm lint`, `pnpm test`, `pnpm build`, and `pnpm test:e2e` pass, and the new spec passes 10 times (`pnpm test:e2e <spec> --repeat-each=10`).
9. **The proof.** Add a link to the list in `components/app-sidebar.tsx`. Add a feature file and a recipe to the feature map of the `verify-fullstack-template` skill. Copy the tenant setup of the recipe of the reference feature. Give one record a long name with no spaces. Run the recipe on a stack, then run `sweep.sh` on it. Done when the sweep prints `sweep: PASSED`, and you read each screenshot and find no text that is cut off: the sweep does not find all of it.

## The cache after a write

| Write | In `onMutate` | In `onSuccess` | In `onError` |
|---|---|---|---|
| Create | | Invalidate `lists()` | |
| Update | Cancel `detail(id)` | Put the answer in `detail(id)`. Invalidate `lists()` | |
| An action, such as cancel | Cancel `detail(id)` | Put the answer in `detail(id)`. Invalidate `lists()` | Invalidate `detail(id)` and `lists()`, because another user can have changed the record |
| Delete | | Remove `detail(id)`. Invalidate `lists()` | |

A write that changes the records of another area also invalidates the lists and the details of that area.
