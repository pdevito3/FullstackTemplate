# The save writes an append-only audit log in its transaction

`AppDbContext` writes the audit log. Each save adds one row to `audit_entries` for each entity that it adds, changes, or deletes, and one row for each action that a handler records. The rows commit in the transaction of the save, or nothing commits. Triggers refuse `UPDATE`, `DELETE`, and `TRUNCATE` on the table.

The capture is a stage of `SaveInStages`, after the domain event handlers. `PrepareWrite` calls `DetectChanges`, touches the owners of changed children, and stamps the entities. Then it compares the original and the current values of each changed entity, and it adds the audit entries to the change tracker. The entries are in the tracker before the execution strategy runs, so a retry sends the same rows.

Each row repeats the facts of its save: the record id, the time, the actor, the MediatR request, and the trace id. The actor is the `sub` and the client ID of the token, and the IDs of the user record and the agent record of the caller. A row names its entity, its aggregate root, and the tenant of the root. The root is the owner at the end of the `Cascade` foreign keys, so the history of a user shows the changes of its permissions. The `data` column holds the old and the new values of the changed properties, or the properties of an action.

The save and `BulkInsertAsync` are the supported writes of an audited table. `BulkInsertAsync` writes many new aggregates with COPY, and their `Created` entries in the same transaction. The build bans the other write APIs in the Server: `ExecuteUpdate`, `ExecuteDelete`, raw SQL, the connection of the context, a new Npgsql connection or data source, and COPY. At run time, `WriteGuard` refuses `ExecuteUpdate`, `ExecuteDelete`, and raw SQL that names an audited table, and raw SQL that runs a DO block, a CALL, or dollar-quoted text. These checks catch mistakes. They do not stop code that wants to skip them: a suppressed ban, reflection, or a `SELECT` of a function that writes.

`GetAuditEntryPage` reads the log with `read_audit_log`. It shows a sensitive value only to a caller with `read_audit_log_sensitive`. Each value of an entity or an action has `[Sensitive]` or `[NotSensitive]`, except a flag, an enum, a `Guid`, an integer, or a foreign key. A unit test fails without a mark. The rules are in [audit-log.md](../backend/audit-log.md).

## Considered options

### Where the capture runs

- **A `SaveChangesInterceptor`.** We did not choose this option. EF calls `SavingChangesAsync` once for each save, outside the retry of the execution strategy and before `DetectChanges`. Thus a retry is not the problem. The problem is that the interceptor comes from DI. The design-time factory and some unit and integration tests build the context by hand, so their saves skip the capture. An audit test then passes or fails by how it built its context. The interceptor also hides a stage that ADR 0010 keeps visible in `SaveInStages`, it must call `DetectChanges` itself, and the bulk insert needs a second trigger.
- **Database triggers that capture the changes.** They also catch raw SQL. We did not choose this option. Each transaction must give the actor, the request, and the trace to the trigger with `SET LOCAL`. A trigger does not know the EF model, so it does not know the aggregate root, the complex properties, or the sensitive values. The map of each table would have a second copy in SQL.
- **A scoped audit service that handlers call.** We did not choose this option. Two objects then own what a save commits: the change tracker and the service. A handler that records on the service of another scope writes nothing and gets no error.
- **Actions as domain events.** We did not choose this option. An action such as "users exported" changes no entity, and only an entity method can queue an event.
- **Save the recorded actions at the end of the request.** We did not choose this option. It needs a second save path outside the handler, and the action of a query commits after its response. `AuditRequestBehavior` throws when a request records an action and does not save it.
- **The request name from an `AsyncLocal` or from `Activity.Current`.** We did not choose these options. An `AsyncLocal` is hidden state, and no other Server code uses one. `Activity.Current` is null when no listener samples the span, and the audit log must not depend on telemetry. The innermost MediatR behavior, `AuditRequestBehavior`, sets the name on the context of the scope.

### The table

- **One table, with the facts of the save on each row.** We chose this option. `AuditEntry` implements `ITenantable`, so the tenant filter applies to it with no exemption. A read needs no join.
- **A table of saves and a table of entries.** We did not choose this option. A save that changes two tenants has no single tenant, so the table of saves needs an exemption from the tenant filter. Each LINQ query in the Server could then read the actor, the request, and the trace of other tenants.
- **One row for each changed property.** We did not choose this option. One change becomes many rows, so the read gets wider and each index gets larger.
- **A hash chain for tamper evidence.** We did not choose this option. Each save must read the hash of the last row, so all writers wait for one another. The triggers make the table append-only with no shared last row.
- **The type name as the stored name of an action.** We did not choose this option. A rename of the type orphans its old entries. Each action has a fixed `[AuditActionName]`, as each permission has a fixed name.

### Writes that skip the save

- **A permit, `Unaudited<T>()`, that opens a set-based write for one type.** We did not choose this option. The permit cannot prove that its SQL writes only the table of `T`. The guarded tables come from the model instead. `[NotAudited(reason)]` on a type that is not a `BaseEntity` removes its table from them, and a unit test asks for the reason.
- **Allow only a LINQ query, a save, and a migration.** We did not choose this option. EF and Npgsql send other commands on their own, with the `CommandSource` `ValueGenerator`, `Scaffolding`, or `Unknown`. The guard decides for each `CommandSource`. It refuses an `Unknown` command only when its SQL names a guarded table. A unit test covers each value, so a new value in a later EF version fails the test until it gets a decision.
- **The run-time guard alone, or the build ban alone.** We chose both. The guard cannot see a command on the raw connection or a COPY, so the build bans those APIs. The build cannot see the words of the SQL, so the guard refuses raw SQL that names an audited table, and raw SQL that runs a DO block, a CALL, or dollar-quoted text, because the guard cannot see the tables that such code writes. A file that suppresses the ban for a `[NotAudited]` table still meets the guard at run time. `BannedApiSuppressionTests` pins the files that suppress the ban.
- **An audited bulk update and bulk delete.** We did not choose this option, because no feature needs one. Postgres 17 has no `RETURNING OLD`, so the old values need a locking read first. That is a load and a save with more code.

### The bulk insert

- **A package such as `Zack.EFCore.BatchInsert.Npgsql`.** We did not choose this option. It must match EF 10.0.13, and it has its own map of the columns. `PostgresCopy` writes the columns of `EntityColumn`, and the audit snapshot reads the same columns, so the two cannot disagree.
- **Clear the change tracker after the insert.** We did not choose this option. `Clear` also detaches the entities that the caller loaded before, and a later change to them is lost with no error. The inserted entities stay tracked and `Unchanged`. Their `Version` is the id of the transaction, which is the `xmin` of each row that the transaction inserted.
- **Refuse each queued domain event.** We did not choose this option. Each root queues a `Created` event, so no entity could be bulk inserted. The bulk insert refuses only an event that has a handler. A save also drops an event that has no handler.
- **COPY with no save events.** We did not choose this option. `TenantLookupInterceptor` forgets a cached miss of each new user after a save. Without it, a new user gets no tenant for up to 30 seconds. The bulk insert raises the save events of EF, so each `SaveChangesInterceptor` sees it as a save.

### The read

- **Offset pages with a total count, as `PagedList` gives.** We did not choose this option. The table only grows, so the count of each page gets slower. A save between two pages also moves the rows, so a row can show on two pages. The read pages with a key instead, newest first, in the order `(occurred_at, record_id, ordinal)`. The response has the cursor of the next page and no total. The name of the feature ends in `Page`, because an endpoint name that ends in `List` must return a `PagedList`.
- **Show the `sub` of the actor to each reader.** We did not choose this option. A provider can make the `sub` an email address. For example, the Authentik seed sets `sub_mode: user_email`. Thus the read shows the `sub` only with `read_audit_log_sensitive`, and `User.Identifier`, which holds the same `sub`, is `[Sensitive]`. The "who" is the purpose of the log, so each row also stores the ID of the user record and the ID of the agent record of the caller. These IDs and the client ID show to each reader with `read_audit_log`. The cached lookup that finds the tenant of the caller also gives the user ID, so the save adds no query.
- **Mark only the sensitive values.** We did not choose this option. A new column with personal data would then show to each reader with no warning. Each value needs a mark, except a flag, an enum, a `Guid`, an integer, or a foreign key. A date, a decimal, or a floating-point number can be personal, for example a birth date or a salary, so it needs a mark too. The read hides a value with no mark, and a value that the code no longer knows.
- **The mark as an EF annotation in the configuration.** We did not choose this option. The mark would sit far from the property, so an author who adds a property does not see it. An action needs an attribute anyway. An annotation also goes into the model snapshot, so a change of a mark adds a migration with no DDL.

## Consequences

- Each save of an entity writes audit rows in its transaction. The rows and the `LastModifiedOn` of the entities have the same time.
- The table only grows. Its key starts with `occurred_at`, and it has no foreign keys, so a later migration can partition it by time with no change of key. Nothing partitions, archives, or drops old rows yet. The retention period is an open decision.
- The table holds personal data in full. The triggers refuse a delete, so the erasure of the data of a person needs a later decision, for example a key for each person that the app can destroy. A read of sensitive values writes no audit row.
- `ExecuteUpdate`, `ExecuteDelete`, and raw SQL fail the build in the Server, and the guard refuses them at run time on an audited table. A change of many rows loads the entities and saves them. Many new rows go through `BulkInsertAsync`.
- The guard reads the words of the SQL. It does not see the writes of a function that a `SELECT` calls, so raw SQL that calls such a function writes no audit row.
- The migration helpers `GrantPermissionToRole`, `GrantPermissionToHoldersOf`, and `DeletePermission` write the permission tables with SQL and no audit row. `GrantPermissionToRole` writes `user_permissions`. `GrantPermissionToHoldersOf` and `DeletePermission` write `user_permissions` and `agent_permissions`. The migration history is their record.
- The save takes the user ID of the actor from the cached tenant lookup of the caller. `User.Identifier` holds the `sub`, and it never changes. No two live users have the same identifier, but a deleted user frees its identifier. Thus one `sub` can name a deleted user, and later a new user who signs up again. The save of the delete and the save of the new user each remove the cached result of the `sub` on their instance, so the next entry on that instance names the live user. An instance that did not save the change keeps the old user ID of the `sub` until its cache entry expires. The entries of that time name the user record that was deleted, also for the saves of the new user.
- The tenant of an entry is the tenant of its root at the time of the save. Each root must have a tenant of its own, so an entity that gets its tenant through `ApplyTenanting` must be a `Cascade` child of its owner. An entity that implements `ITenantable` must be a root. A value object must map with `ComplexProperty`, not `OwnsOne`. Unit tests over the model enforce these rules.
- A lost acknowledgment of the commit still gives a 409 for a save that committed (ADR 0010). The audit rows do not change this. `BulkInsertAsync` closes this gap for itself. After a failed commit, it looks for its record id in `audit_entries`, and the rows are there when the commit succeeded.
- `BulkInsertAsync` refuses a context with pending changes, a type that is a child of an owner, and a queued event that has a handler. It tracks each row that it writes, so a caller splits a very large import into parts.
- The migration `GrantAuditLogPermissions` gives the two new permissions to each admin. ADR 0009 says that an old server cannot load a user with a row of a permission that it does not know. In a rolling deploy, the first new instance applies the migration, and each old instance then fails each load of an admin until it stops. Deploy this change with no old instance that serves requests after the migration. Or ship the permission names one release before the migration that grants them.
- An old instance has no audit capture. In a rolling deploy, each old instance writes its changes with no audit entries until it stops, so the log of each entity is complete only from the time when the last old instance stopped.
- The log is the only record of who changed an entity and when. The migration `DropWhoAndWhenColumns` drops `CreatedOn`, `CreatedBy`, `CreatedByClient`, `LastModifiedBy`, and `LastModifiedByClient`, which held the actor and the time of the first and the last change. Its `Down` adds the columns back with no values, and `CreatedOn` as `-infinity`, which the app reads as `DateTimeOffset.MinValue`. A row from before the log has no `Created` entry, so the drop loses its creator and its creation time. `LastModifiedOn` stays, because the owner touch marks it modified, so EF writes the owner row and its `xmin` changes (ADR 0008).
- An old instance still maps the dropped columns, so each query of a user, a tenant, an agent, or a permission fails on it after `DropWhoAndWhenColumns` runs. The permission guard reads the user or the agent on each request, so an old instance fails almost each authenticated request until it stops. Deploy this change with no old instance that serves requests after the migration.
- `GrantPermissionToRole` checks whether `user_permissions` has `created_on`, because the migrations before the drop also call it.
